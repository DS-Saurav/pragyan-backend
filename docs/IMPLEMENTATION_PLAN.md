## B. How to read the statuses

Every roadmap item carries exactly one status:

| Status | Meaning |
|---|---|
| **Verified current gap** | A defect, gap, or missing capability confirmed by reading the current source/documentation on 2026-10-26. The gap exists today; the fix has not been built. |
| **Needs investigation** | The true current state is unknown, or only known from stale documentation; investigation is scheduled **before** any repair. |
| **Proposed** | A new capability with no current implementation, recorded as owner-directed product direction but not yet built or agreed in detail. |
| **Blocked by owner decision** | Work that cannot finalize its acceptance criteria or approach without an owner-provided input (e.g., a marksheet sample, a vendor, a numerical target, or the missing audit report). |

**Security-finding statuses additionally distinguish:** documented observation with evidence in current source (**Verified current gap**), finding that verification shows already fixed (recorded as such in Section D), and finding whose state depends on the unlocated audit report (tracked under **O-1** until evidenced). Nothing is claimed fixed without evidence, and nothing is claimed unconfirmed without saying why.

**One standing prerequisite (Phase 0)** — kept because it is lightweight verification preparation useful to *both* feature completion and remediation:

- **P-0.1 Establish a trusted test baseline.** **Update recorded during Stage D1 (2026-11-01); the run itself belongs to the U1.1 stage completed before D1:** the full suite **has now actually been executed once** in this project's records — result: **289 tests / 1,426 assertions, all passing**, with U1.1's Library guard fix, Document failure-safety fix, and hero render test included. This supersedes the reservations below where U1.1's run applies; the distinctions (files on disk ≠ tests discovered; discovered ≠ executed; executed ≠ passing) are kept for everything *after* that run: **40 `*Test.php` test files plus the `TestCase.php` test-support class now exist on disk, and any stage adding or removing tests must report changes against U1.1's 289/1,426 baseline, explaining intentional additions and removals.** No test was executed during Stage D1 — the 289/1,426 figure is the **U1.1-reported baseline, not a D1 run**. *Status: baseline recorded (U1.1-reported); ongoing maintenance is a literal standing duty.* Priority: any implementation stage later than U1.1 re-runs (or samples from) this baseline per its own DoD. DoD per stage: recorded run result, with gains or losses explained. Verification: each stage's run log. Risk of proceeding without it: regressions from Option C implementation stages would go unnoticed.

**Parallel housekeeping — explicitly not a gate for Phase 1:**

- **H-0.2 Reconcile stale documentation.** Section D of this plan lists places where `IMPLEMENTATION_STATUS.md` and `TESTING_AND_DEPLOYMENT.md` contradict the PRD's re-verified state. This reconciliation **must not block or delay feature work**; it runs in parallel with Phase 1, or as a later documentation-maintenance task, whichever the owner prefers. *Status: Verified current gap (stale docs).* Priority: parallel/out-of-band (documentation maintenance only). DoD: each row in Section D is re-checked against source and the owning docs are updated in a separate, approved doc-work stage. Risk if postponed: some effort spent on already-fixed issues — an efficiency concern, not a schedule blocker.
